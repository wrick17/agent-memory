## Decisions and workflow

- Hosted capture uses digests only while retaining local learning parity. Phase 2 uses both dummy live sessions and recorded fixtures in the test profile, with cleanup. [Requirements](../research/00-requirements.md#confirmed-decisions), [phase 2](architecture.md#phase-2-capture-backups-and-the-first-rehearsal).
- No benchmarks or early optimization are phase gates. Free-plan limits are not gates; the owner's target is Paid. [Plan](architecture.md#22-implementation-plan), [requirements](../research/00-requirements.md#confirmed-decisions).
- The owner approved the final implementation plan on 2026-10-28. This authorizes its build, deployment, configuration and tests. DNS changes still require explicit approval one at a time; hook trust needs owner interaction, and the owner chooses the cutover window and gives the go. [Owner actions](architecture.md#owner-actions).
- Opus-owned work waits for the usage reset; do not substitute Sol for Opus on this project. This is a workflow rule, not a product feature.
- Auth topology, confinement, hook trust and digest parity require the checks and safe failure outcomes in [open questions](architecture.md#open-questions). The [latest review's A/B/C cases](review-sol-v31-2026-10-28.md#remaining-material-issues) are design-closed by the bounded v3.2 source check recorded above; their runtime checks remain pending.

## Maintenance

1. Before a product behavior, interface or decision change, read this manifest and the linked authoritative sections for affected features.
2. In the same change, update every affected entry, phase and status; link the specific implementation and relevant check evidence. Add an ID for a new commitment and retain existing IDs.
3. Record intentional decision changes with their reason, date and superseded decision or source. Preserve a link to the prior record instead of silently rewriting history. Record known deferrals and unresolved design findings explicitly.
4. Mark a feature implemented only when its promised behavior exists. Mark it verified only when the relevant check actually passed, with a link to the result and its scope. Design documents and reviews are not implementation or runtime verification.
