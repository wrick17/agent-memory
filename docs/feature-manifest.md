# Agent Memory feature manifest

This is the commitment index. [Confirmed requirements](../research/00-requirements.md#confirmed-decisions) govern product intent; [architecture v3.2](architecture.md#decisions-at-a-glance) describes the approved design and phase checks. The owner approved the final implementation plan on 2026-10-28 with "Let's build it", then authorized all necessary non-deleting changes without further approval prompts. Implementation may proceed through the planned phases; runtime claims still require their implementation checks.

**Status baseline:** Every feature below is planned and none is verified. On 2026-10-28 phase 1 was implemented in part for AM-01, AM-02, AM-03, AM-05, AM-06 and AM-07, with local tests and selected live evidence; their rows say what exists and what is still unproven ([phase 1 implementation](phase-1-implementation.md)). Phase numbers refer to the [proposed plan](architecture.md#22-implementation-plan); C means final rehearsal and cutover. The [v3.1 closure review](review-sol-v31-2026-10-28.md#six-closure-verdicts) closed export ties, publish-before-commit recovery and confinement in the design, alongside previously closed F2, F5, F6, F9 and F10. These are design closures, not passing runtime checks. Auth, confinement, real capture parity, recovery, wipe and migration still require their phase checks.

## Decisions and workflow

- Hosted capture uses digests only while retaining local learning parity. Phase 2 uses both dummy live sessions and recorded fixtures in the test profile, with cleanup. [Requirements](../research/00-requirements.md#confirmed-decisions), [phase 2](architecture.md#phase-2-capture-backups-and-the-first-rehearsal).
- 2026-10-28, parent decision under the owner's authorization: recall's semantic enrichment (query embedding plus Vectorize query) has one 3 s deadline. It supersedes the 300 ms Vectorize wait and the 1 s embedding bound, because live latency excluded every semantic result under them. Three seconds is a product budget, not a latency guarantee. [Evidence](phase-1-implementation.md#live-vector-channel-diagnosis), [change](phase-1-implementation.md#semantic-deadline-change), [design](architecture.md#11-search-and-recall).
- No benchmarks or early optimization are phase gates. Free-plan limits are not gates; the owner's target is Paid. [Plan](architecture.md#22-implementation-plan), [requirements](../research/00-requirements.md#confirmed-decisions).
- On 2026-10-28, the owner deferred second-machine checks: "We'll do that later. Test on this system first." Run live Claude Code, Codex and headless-token checks on the current system first. Keep physical cross-machine verification explicitly pending; local clients do not prove it.
- On 2026-10-28, the owner superseded the earlier individual DNS and non-deleting change approval gates: "No need to ask for approvals, you can make all the changes you need short of deleting stuff". Necessary non-deleting configuration, DNS, deployment and implementation may proceed without another approval. Deleting data or resources still requires approval. Provider sign-in and hook trust may still require owner interaction; runtime phase gates and cutover rehearsal and rollback safeguards remain required. The [earlier owner actions](architecture.md#owner-actions) are retained as the prior decision.
- Opus-owned work waits for the usage reset; do not substitute Sol for Opus on this project. This is a workflow rule, not a product feature.
- Auth topology, confinement, hook trust and digest parity require the checks and safe failure outcomes in [open questions](architecture.md#open-questions). The [latest review's A/B/C cases](review-sol-v31-2026-10-28.md#remaining-material-issues) are design-closed by the bounded v3.2 source check recorded above; their runtime checks remain pending.

## Maintenance

1. Before a product behavior, interface or decision change, read this manifest and the linked authoritative sections for affected features.
2. In the same change, update every affected entry, phase and status; link the specific implementation and relevant check evidence. Add an ID for a new commitment and retain existing IDs.
3. Record intentional decision changes with their reason, date and superseded decision or source. Preserve a link to the prior record instead of silently rewriting history. Record known deferrals and unresolved design findings explicitly.
4. Mark a feature implemented only when its promised behavior exists. Mark it verified only when the relevant check actually passed, with a link to the result and its scope. Design documents and reviews are not implementation or runtime verification.
