## What exists

| Piece | Files | Behavior |
|---|---|---|
| Schema v2 | `src/profile/schema.ts` | Capture columns on `texts` (`range_id`, `capture_part`, `sha256`, `capture_status`), the `texts_capture` unique index, `captures_fts` kept to live capture-lane rows by triggers, `markers`, and `maintenance`. Seq indexes and tombstones on the new tables. |
| Capture lane | `src/profile/capture.ts`, `src/profile/store.ts` | A part's identity is `(range_id, capture_status, part_id)` plus the SHA-256 of its exact bytes. The same identity with the same hash replays; with another hash it is refused (`hash_conflict`). Each part is at most 8 KB. The body schema is strict at every level (`asks`, `decisions`, `corrections` items of exactly `text` and `pos`; `outcomes` of only `commits`, `prs` and `tests`; `entities`; `dropped`), and every string is at most 160 characters (asks) or 280 (everything else, outcomes and entities included). The server stores the exact uploaded bytes; it refuses a part in which redaction would still change a string (`needs_redaction`), and never rewrites one. The schema has no field for a raw transcript record or unbounded text. It cannot show that a short excerpt is not a whole short message: a message shorter than its limit can appear in full as one bounded excerpt. A manifest is stored only when its spans tile the range with no gap or overlap and every listed part is stored with that hash and drops no decision or correction. It is checked and stored in one transaction. The heuristic digest then leaves the capture index. Each part queues `unprocessed_capture`, and parts with corrections also queue `preference_signal`. Digests sit on a `session` node with no embedding card and no `memory_type`, so ordinary recall and the inventory never see them. |
| Hosted API | `src/api.ts`, `src/worker.ts` | `POST /v1/ingest` uploads digests and manifests. `POST /v1/capture` returns the server's parts and manifest state per range, for recovery. Both need the job token's `ingest` scope, use a strict schema, route like a write (bound profile, explicit profile, repo rules, device default) and never go to `me`. |
| Local client | `local/agent-memory.mjs` (Node 24, no dependencies) | Commands `hook <client>`, `run` and `install`, detailed below. |
| Phase-2 tools | `src/mcp.ts`, `src/profile/write.ts`, `src/profile/read.ts` | `capture_memory` stores a candidate (kind `other`, label `capture`, status `candidate`) whose text sits in the capture lane, outside recall and inventory. `review_candidates` lists by BothQ status (`pending`, `promoted`, `dismissed`, `all`), promotes into a new memory linked to the capture by a `relates_to` edge and `node` evidence in one transaction, or dismisses with a required reason. `record_knowledge` upserts entity nodes by key, else by kind, scope and name. Every edge an agent writes is a judgment edge with a reason of 8 to 600 characters and at least one evidence pointer. `end[]` closes an edge as history, and a decision needs `why`. New `work` project, component, person, ticket, feature and bug names and keys are added to the `me` guard's sensitive terms before the response. All three use the existing write path, routing, request binding, replay and `me` guard. Captures never go to `me`, and `me` takes no person nodes. |
| Confined runtime | same file, `confinedRunner()` | A throwaway `CODEX_HOME` holding the section 12 config (mode 400, hashed) and the output schema. The owner's Codex login is linked in for the Codex process only. Positive controls run first, then classified denial probes under the same config, then `codex exec --ephemeral --json --output-schema` with the subrange on stdin. `parseEvents()` accepts only the known event envelopes (`thread.started`, `turn.started`, `turn.completed`, `item.started`, `item.updated`, `item.completed`) and, inside item events, only reasoning items and the final agent message: any other item is a tool event that discards the run and marks the range `stuck`; an unknown envelope, such as a new runtime or configuration notice, is a `runtime_warning` that leaves the range pending. Unknown output fails closed. On any platform other than macOS the runtime is `indeterminate`. |

**What the local commands do.**
- **`hook`:** writes a private trigger file (mode 600) with a fresh generation id and starts a detached `run` if no live process holds the lock. It does no network I/O and never stores `last_assistant_message`.
- **`run`:**
  - Takes the machine lock by hard link (exclusive create; a lock whose process is dead is removed only by the one worker that creates its reclaim marker), replays the spool, and debounces each session (45 s idle, at most 10 minutes). The run stays, sleeping, until each queued trigger is due, claims each trigger generation by an atomic rename before handling it, and handles any newer trigger that arrived meanwhile before it exits.
  - Finds the transcript: the hook's path, else the Codex session store or the Claude Code project folder. With no file, the session stays pending for up to 7 days and nothing is acknowledged.
  - Fixes the epoch when the session is first read (hash of the first min(size, 4 KB) bytes), then checks those bytes on each run and extends the check toward 4 KB as the file grows, so an append keeps the epoch and a rewrite starts a new range sequence. Reads complete lines only, keeping owner and assistant text. Tool calls and output, thinking, `<system-reminder>`, meta lines and injected Codex or Claude context are skipped.
  - Redacts with the server's patterns. Writes the range's text to a mode-600 pending file and uploads a bounded heuristic digest labeled `heuristic`. A network failure spools it; a refusal is recorded.
  - Consolidates every kept pending range, whether or not the source transcript can still be found, in parts: subranges of at most 32 KB at message boundaries, halved down to 2 KB, with three attempts at the floor. A part is accepted only if it passes the same strict body schema as the server (`bodyProblem`), fits 8 KB, drops no decision or correction and keeps every owner literal present (backticked, quoted, path-like, ticket keys). Accepted bytes go to `pending/<range>.parts/` before upload and are never regenerated. Parts the server holds take precedence. Lost part files are adopted from `POST /v1/capture`, and only uncovered spans are digested.
  - Uploads the parts, then the manifest. Only after the manifest is stored does `consolidated_to` move, over contiguous consolidated ranges of the current epoch. The acknowledgement is saved before that range's pending text and part files are deleted, so a crash during cleanup leaves an acknowledged range whose leftovers the next run removes. A range whose text is gone is first checked against `POST /v1/capture`: a stored manifest is adopted; otherwise the range is `stuck`.
  - If no runtime is available, ranges stay pending with their heuristic digest. A failing range is `stuck`, and stuck ranges keep their local text.
- **`install`:** copies the CLI to `~/.agent-memory/bin/agent-memory`, writes a private `config.json` with the server, a token file path and the model, creates the probe folder, and prints the Claude Code and Codex hook entries. It never writes client settings, installs hooks or trusts them.

**Runtime config adjusted to Codex 0.165.0 (evidence-driven).** The first real `codex exec` reported `Codex is ignoring 1 unrecognized configuration setting: tools.view_image`. `codex features list` shows `browser_use`, `browser_use_external`, `computer_use` and `image_generation` enabled by default. The design's config predates them. The runtime config therefore drops `[tools] view_image` and sets those four features to `false`. Any `error` item from Codex, such as an ignored setting, now fails the run as `runtime_warning`, and the range stays pending. That is fail-closed: the runtime is not the one the probes proved. Section 12 of the architecture now carries the same change ([design](architecture.md#the-daily-batch-runs-confined-or-not-at-all)).

**Platform check on this Mac** (Codex CLI 0.165.0, throwaway `CODEX_HOME`, no global configuration touched). The design's `am_batch` profile loads, and `codex sandbox -P am_batch` runs `/bin/echo`. It denies reads of the home canary, the temp canary and the home listing with "Operation not permitted". Network is denied too, but curl prints the classified message ("Immediate connect fail for 1.1.1.1: Operation not permitted") only with `-v`, so the network probe uses `curl -sS -v`. Without `-v` it would have been `indeterminate` and every run skipped.

## Not proved, and gates still open

- **Real-model parity.** One real confined `codex exec` (default model `gpt-6-luna`, low effort) consolidated a three-message dummy fixture on this Mac. Probes classified `denied`. The event stream was `thread.started`, `turn.started`, one `agent_message`, `turn.completed`. The part passed every acceptance check and kept the marker-free correction and the backticked path. One small canary is not parity. The stub keeps every sentence, so the fixture checks prove the protocol, not a model's recall. Checking that the reviewer-marked decisions and corrections survive real consolidation on recorded sessions and a long transcript is the pending parity gate.
- **Event names** `item.completed` and `agent_message` were confirmed by that run. `reasoning` items are allowed but none appeared at low effort. Any other item type still fails closed.
- **Live end to end:** a private, configured dummy session through a job token against the deployed Worker, after Terra's review and deployment. Hook trust for Codex under T3, and installing hooks into real clients, remain owner steps.
- **Not built in this vertical:** repo markers and work-item uploads (phase 5); the daily batch, leases and maintenance tools (phase 3); links across profiles in `record_knowledge` (phase 3); Next, by owner priority (2026-10-29), is the [import vertical](architecture.md#import-vertical-bothq-and-curated-markdown-memory): a read-only, resumable, idempotent copy of BothQ and the curated Markdown memory into the hosted profiles for review, with BothQ still the only live system. Backup and restore are built and tested in the [final backup stage](architecture.md#final-stage-backup-and-restore), and cross-machine parity runs in the final combined rehearsal (owner decisions, 2026-10-29).

## Deviations and interpretations

- The heuristic digest is best effort. A refusal is recorded and never retried, a network failure spools it, and neither counts as captured.
- A range with no owner or assistant text is consolidated with one empty part, so the manifest still tiles it.
- The pending file holds the range's extracted, redacted messages as JSON, so consolidation and gap recovery keep each message's transcript position.
- If both the pending text and the part files are lost, the range is `stuck` with `pending_text_missing`. Nothing is invented.
- The network probe uses `curl -sS -v` (see the platform check above).
- Maintenance items for a consolidated range are one `unprocessed_capture` and, when any part has corrections, one `preference_signal`, both keyed by the manifest hash (review fix F8; the design said one per part).
- New work terms are registered before the work write. If that write then fails, the extra terms over-guard `me` until the nightly rebuild.
