## Goal

One hosted "second brain" for all of the owner's coding agents (Claude Code, Codex, T3 Code) on every machine. It records everything agents come across, keeps a rolling journal, learns a model of the owner (facts, preferences, choices), links projects, repos, people and tools, and cleans itself up so it does not bloat. It replaces local BothQ and the native memory of Claude Code and Codex.

## Confirmed decisions

| Area | Decision |
|---|---|
| Hosting | Owner's personal Cloudflare account on the Workers Paid plan, at `memory.wrick17.com` (DNS already on Cloudflare). Cloudflare-managed services only. Uptime matters. No offline mode: without internet the agents' models do not work either. |
| Server role | Cloudflare memory is only memory: storage (profiles, revisions, idempotency, supersession, history), retrieval (FTS5, literal, RRF, entity traversal, timelines, deterministic read-time views such as priority ranking), auth checks, dashboard, and deterministic housekeeping. Everything else is done by the owner's agents and written or removed through MCP (owner, 2026-10-28 18:05 IST; supersedes earlier server-side processing decisions).  Refined 18:15 IST: a storage system that understands how everything links to everything, never an autonomous agent acting on the owner's behalf. Link model (confirmed 18:35 IST): server indexes deterministic identifier links (repos, tickets, PRs, file paths, people, sessions, journals, supersession, time adjacency) and embedding-similarity related edges without an LLM; agents add judgment links via MCP; retrieval exposes traversal, connected-to queries, link-expanded recall and a dashboard map; deterministic retention (unused captures removed after 90 days, archive purged after 300 days, exact dedupe, size budgets, logged with undo) is storage policy, not agency. |
| Knowledge model | Core purpose (owner, 2026-10-28 18:25 IST): understand projects, the people who worked on them, bugs, features, architecture, and how everything links and why. Confirmed 2026-10-28 18:45 IST: typed graph with a fixed core ontology (entities: project, component, person, bug, feature, ticket, PR, commit, release, decision, rule, preference, session, journal, document; relations: works_on, authored, reviewed, reported, assigned, part_of, depends_on, implements, fixes, introduced_by, caused_by, blocked_by, decided_because, supersedes, contradicts, relates_to; promotable `other`); judgment edges and decisions require a short reason plus evidence pointers; edges carry valid_from, valid_to, recorded_at so history stays queryable; people stored as names, handles, roles and work only, colleagues only in the work profile; files are evidence pointers, not entities; server derives identifier edges deterministically, agents add judgment edges with reasons; entity pages, path-with-reasons queries, link-expanded recall and a visual map. |
| Free plan | Target the owner's Workers Paid plan for now (owner, 2026-10-28). Keep the design Free-friendly where it costs nothing extra, but Free-only limits (for example the 10 ms CPU per request) are not phase gates; revisit them if Free-plan self-hosters appear. Only the corpus module is explicitly Paid-only. The server runs no LLM work beyond embeddings. |
| Storage | SQLite (Durable Object SQLite chosen by the architecture), not Neo4j or any external graph DB. Owner was explicit: "SQLite as long as we can keep it in the free plan". Graph = typed entity and edge tables. Semantic recall via Workers AI embeddings in Vectorize from day one (owner leaning, recommended): one namespace per (user, profile), treated as a rebuildable index (re-embed from stored text after a restore), so the profile Durable Object stays the source of truth. Vectorize is on Free (5M stored dims, 30M queried dims/month) and Paid (10M/50M included), per its pricing page updated 2026-04-21. Refined in architecture v3: the Vectorize namespace is per (user, profile, generation), one active namespace per profile, so scratch and old restore generations cannot overwrite or delete live vectors. |
| Auth | New Clerk application named "Agent Memory" (owner already has Clerk apps "Bot Dashboard" and "Postplan"; owner authorized creating and configuring the new one through the Clerk dashboard at build time). Browser OAuth for interactive clients. Revocable per-device tokens, created in the web UI, for headless machines. Choose between Clerk-as-authorization-server and `workers-oauth-provider` fronting Clerk after a real-token test of Clerk's RFC 8707 audience binding and loopback any-port redirect matching. |
| Profiles | Start with `me`, `work`, `personal`; more can be added later. Each profile is its own isolated store. Every profile can read `me`. `work` and `personal` cannot read each other. Work data goes in the work profile of the personal Cloudflare account (owner's decision). Clarified 2026-10-28 (owner): "Isolation is important but not at the cost of continuity. There will rarely be links cross profiles, if there are, then let them be linked." and "The separate profiles are mainly to separate project context, and maybe wipe the work profile if I leave the company someday." Profiles separate default project context and allow independent work deletion. Real cross-profile links keep stable endpoints, reason, evidence and provenance through moves; the owner can explore them explicitly; scoped device tokens see only an opaque id for targets they cannot read; default recall stays contextual. An owner-only work wipe removes the profile's stores, vectors, corpus, transfer copies and exports, keeps opaque backlinks and intentionally company-free `me` preferences, and leaves a durable tombstone so no restore or import resurrects it; physical erasure inside Cloudflare follows the platform's own retention. |
| Routing | Writes carry repo identity. Server rules match git remote (for example GitHub org `Sequoia-Engineering` means work) or path prefix, then the device's default profile, with an explicit per-call override. Unmatched migrated records go to a review list. |
| Memory contract | Keep the BothQ memory contracts: stable ids that survive renames and scope moves, revisions (snapshots plus append deltas), `request_id` idempotency with payload-hash conflict detection, `expected_revision` optimistic concurrency, supersession, retirement with history, candidates and promotion, rules, references, routines with ordered steps, rolling task journals with atomic appends, literal plus full-text recall with passages and token budgets. |
| Model of the owner | Stated preferences become active. Inferred preferences go live automatically, labeled "inferred" with evidence, treated as hints, outranked by stated ones; the owner can pin or delete them in the dashboard. Work-learned preferences about the owner go to `me` when they carry no company details. |
| Capture | Explicit agent writes plus an end-of-session digest sent by one shared hook script for Claude Code and Codex (what was done, decisions, repos, outcomes, owner corrections). No raw transcripts or tool output. Server-side secret redaction on every write. Capture must record at least as much as Codex's own memory generation does today. Clarified 2026-10-28 (owner, during the v2 review): hosted capture stores only locally prepared digests, never whole user or assistant messages. This covers ingest, spools, logs, backups and the session corpus. The local run reads the complete input, keeps learned decisions, corrections and provenance in bounded redacted digests with evidence positions, and acknowledges an immutable input range only after its digest is durably stored. The final migration turns old `session_messages` content into digests and accounts for that in verification; corpus import never bypasses this. |
| Learning and cleanup | Automatic, no approval queue, but performed by the owner's agents through MCP, not by the server (2026-10-28 18:05 IST). The server runs only deterministic housekeeping without an LLM: removal of captures not promoted or recalled within 90 days, 300-day archive purge (owner, 18:35 IST), exact-hash dedupe, size budgets, activity log with undo, and a deterministic maintenance queue of records needing attention. Agents do judgment work: inline at task end (compact own journal, promote durable facts) and in the debounced end-of-session detached run (at most once per profile per day; `codex exec`, Luna mechanical, Terra judgment) that pulls queue batches (duplicates, contradictions, entity linking, preference inference, stale journals). Never auto-delete owner-stated rules or preferences or anything in `me`. Removed items archived 300 days. |
| LLM compute | None on the server. All LLM work runs in the owner's agents (Claude Code, Codex; one-time distillation via local Codex on the ChatGPT subscription). Workers AI only for embeddings as an internal binding (about 100-300 neurons/day), switchable off for FTS5-only recall. Confirmed 18:35 IST. |
| Work graph | Cloudflare never accesses GitHub or Jira and holds no GitHub/Jira credentials; repos and Jira are private (owner constraint, 2026-10-28 17:50 IST, supersedes server-side sync). GitHub and Jira data enters only from the owner's machines while work is done: the end-of-session hook's debounced detached run uploads new commits (local git), PR metadata (local `gh`), and Jira context for tickets the session touched; agents also record ticket/PR context through MCP tools during work; a default once-a-day local refresh of assigned Jira tickets (work only) and open PRs (both profiles), triggered by the first session end of the day, can be turned off. Tickets, priority board per profile and strategic review are computed on Cloudflare over uploaded data with as-of dates and cover only what the owner's machines uploaded. |
| Bots | The BothQ bot fleet (architect, QA, observer agents) is not needed and retires. |
| Machine dependency | After the one-time migration, nothing recurring may depend on the owner's machine; everything runs on Cloudflare within quota. One-time work (migration distillation, corpus bulk load) may run locally; the owner will leave the machine online for it. Capture hooks run on client machines only while agents run, which is inherent (clarified 2026-10-28 17:00 IST). Exception (2026-10-28 17:35 IST): corpus tables derived from scanning code checkouts (frontend, architecture, pattern analyses) refresh opportunistically on the owner's machine. The end-of-session hook checks whether the session's repo changed since its last analysis; if so it starts one short detached run (no resident process, no launchd) that analyzes only changed files in the local checkout (deterministic scanners as scripts, `codex exec` with Luna/Terra only where judgment is needed) and uploads with a job-scoped token. Debounced to once per repo per day; tables show an "as of" date; untouched repos keep their last snapshot. No server-side fallback; Cloudflare never fetches from GitHub. |
| Corpus | Needed. One corpus per profile. A local uploader CLI does the one-time bulk load from local git repos and agent session databases. Incremental updates come only from the owner's machines through the end-of-session hook (new commits, PR metadata, changed-file analyses) and capture digests for sessions. No server-side GitHub fetching and no server-side Workflow fallback. Paid-only optional module. The existing 3.2 GB Sequoia corpus moves first. Built in the last phase. |
| Dashboard | Rich visual overview of the entire memory, simple enough for non-technical people at the top level, with detailed data when drilling down: profiles, timeline, entity map, journals, model of the owner, activity log with undo, devices and tokens, routing rules. |
| Native memory cutover | Import Claude Code memory files (17 on this Mac under `~/.plaude/projects/*/memory`) and Codex memories (`~/.codex/memories`: `MEMORY.md` 436 KB, `raw_memories.md` 1.1 MB, 656 files including rollout summaries). Then disable Codex `generate_memories`/`use_memories` and Claude Code auto memory, rewrite the owner's dotfiles instructions and the `bothq-memory` skill to use the hosted server, and archive the old files. |
| Migration | BothQ stays the system of record during the whole build; no dual writes (owner, 2026-10-28). Phases are verified with test data and dry-run migrations into a test profile. Once everything is built and confirmed working, one final full migration moves all data (BothQ adopted and legacy shapes, Claude Code and Codex native memories, the corpus), it is verified, agents and hooks are switched over, native memory is disabled, and BothQ is shut down. Current-state snapshots with dates and provenance, routed to profiles, `sequioa` typo fixed. Runs locally through Codex in resumable batches with checkpoints and idempotent request_ids, rerunnable; distillation also emits entity links and routing. Refined 2026-10-28 (v2 review): BothQ request records (operation, hash, result) and original revision history import mechanically and losslessly, separate from semantic distillation, and replay is verified with identical and changed payloads. Rehearsals run in phase 2, after phase 3, and as a combined final rehearsal before cutover. Cutover takes a byte-exact snapshot of configs, instructions, skills and native memory files, keeps ordinary sessions frozen through smoke checks, and rolls back by restoring that snapshot; no dual writes. |
| Outbound access | Clarified by the owner (2026-10-28): "no internet interaction" means the server never calls GitHub or Jira and holds no credentials for them. Other outbound calls are fine where needed, for example fetching Clerk's JWKS or calling Clerk during login. The server still never acts as an autonomous agent and runs no server-side LLM judgment. |
| Backups | Cloudflare only (owner, 2026-10-28 18:35 IST): Durable Object point-in-time restore plus a nightly encrypted export to R2, keeping only the 2 most recent exports. No Google Drive. |
| DNS | At build time, add the Worker route for `memory.wrick17.com` and Clerk's records on `wrick17.com`, asking the owner before each change. |
| Open source | Self-host template that others deploy on their own Cloudflare and Clerk accounts. Not a shared multi-tenant service. Records still carry a user id. |

## Data facts to design for

- About 1,100 memories and 5.5M characters in BothQ; 94.5% is 706 task journals; largest journal 987k characters and 664 revisions.
- About 99 writes a day, append-dominated; zero user memories; almost no links from memories to tickets, repos or people; recall today is text search only.
- Corpus: 525k commits, 292k tickets, 135k PRs, 1.7M search documents, 3.2 GB.

## Open risks for the design to resolve or gate

- Clerk audience binding and loopback redirect matching (auth topology decision).
- Vectorize availability on the Free plan (docs conflict).
- Durable Object SQLite per-object storage on Free (docs say 1 GB in one place, 10 GB in another).
- MCP handler CPU per request against the Free plan's 10 ms limit.
- Claude Code and Codex hook events available for end-of-session digests, and how to disable Claude Code auto memory.
